## 一、正常扫块做什么

例如数据库记录已经扫描到 `1010 / H1010`：

1. 先向节点查询 1010，确认它仍然是 H1010。
2. 读取 1011 的区块和执行回执，再次核对 1011 的 Hash 没变。
3. 确认 1011 的父 Hash 是 H1010，再解析 TRX 和 TRC20 充值。
4. 有充值就发 Kafka 并等待 Broker ACK；空块直接进入下一步。
5. 一个手动事务保存 1011 摘要、将检查点推进到 1011。每到整百高度才同时清理旧摘要，1011 不触发清理。

每轮开始检查末块，是为了发现上一轮之后发生的分叉；每块检查父 Hash，是为了发现本轮扫块期间发生的分叉。

## 二、为什么读取区块要请求三次

| 次数 | 读取什么 | 作用 |
|---|---|---|
| 第一次 | 区块和交易列表 | 得到区块 Hash、普通 TRX 转账和合约调用内容 |
| 第二次 | 执行回执 | 从 Transfer 日志得到实际 TRC20 转账的付款方、收款方和数量 |
| 第三次 | 同一高度的区块 Hash | 检查前两次读取期间区块是否被替换 |

例如第一次读到 `1011 / A`，第三次读到 `1011 / B`，本次区块与回执都丢弃，由节点管理器整体重读。

三次都使用同一个 FullNode。Hash 复核可以检测读取期间可见的分支变化；充值最终是否有效，仍由 chain-server 固化确认。

## 三、发生分叉怎么恢复

本地已经扫描到 1010，最近的摘要与节点比较如下：

| 高度 | 本地 Hash | 节点 Hash | 是否相同 |
|---:|---|---|---|
| 1000～1007 | 原 Hash | 原 Hash | 相同 |
| 1008 | Old1008 | New1008 | 不同 |
| 1009 | Old1009 | New1009 | 不同 |
| 1010 | Old1010 | New1010 | 不同 |

处理顺序：

1. 固定一个 FullNode，在本地保留的摘要中二分查找。
2. 找到最后相同的 1007，复查末块、1007 和 1008。
3. 一个事务将检查点退到 1007，并删除 1008～1010 的旧摘要。
4. 本轮正常结束，不发送新分支充值。
5. 下轮从 1008 重扫，保存新 Hash，有充值则重新发送 Kafka。

`1007` 是最近的共同区块，由 Hash 比较找到。最早保留的摘要只是查找下界，不代表固化点。

已发送的旧分支消息不会从 Kafka 撤回。同一交易重新打包时可以再次发送；chain-server 通过幂等键和后续固化确认处理这些记录。

## 四、最近 1 万条连续保留，更早的历史少量保留

`blockHistorySize` 默认 **10000**，通常不用配置。更早的历史每 1000 块留一条，最初起点也保留，仍使用同一张摘要表。

例如从 100 开始，扫描到 20000：

| 范围 | 保留什么 |
|---|---|
| 最近 1 万条 | 10001～20000，每块一条 |
| 更早历史 | 99（初始起点）、1000、2000、……、10000 |

如果真正共同区块是 8500，最近 1 万条全都不同，程序还会查旧摘要：8000 相同、9000 不同，就自动退到 8000，下轮从 8001 重扫。只比精确回退多重扫 500 块，不会因为近期窗口已经清理而一直报错。

这些保留点只是实际扫过的高度和 Hash，仍需与节点核验，不代表已固化。旧数据不加载到内存，正常每扫 1000 块才增加一条长期记录。

清理每 100 个高度执行一次：20000 清理后，20001～20099 只保存摘要和推进进度；20100 再清理。期间最多暂时多保留 99 条连续摘要，重启后仍按整百高度执行，无需额外配置。

| 清理位置 | 删除什么 |
|---|---|
| 正常推进 `pruneHistory` | 整百高度才压缩旧历史，保留初始起点和每 1000 块的摘要 |
| 分叉回退 `rewind` | 共同区块之后的旧分支摘要，准备重扫 |

如果连最初的 99 也被替换：自动读取新的 99 Hash，事务重置边界、回退检查点并删除后续旧摘要。下轮从 100 重放整个已记录范围，当前配置起点不会改变它。只有找不到任何共同摘要时才使用这个兜底。

数据库摘要缺失属于其他异常，不能用节点现在的 Hash 伪造旧历史；旧版本已经删除的 Hash 也无法凭空还原。

- 穷举 1000 条连续历史内的全部 **999 个分叉边界**，共同区块正确，单次节点读取不超过 16 次（含边界复查）。
- 本地 HTTP 节点、真实解析器、MyBatis 和事务验证：空块、单笔、多笔充值、发送失败、重启恢复、1/2/5/7 块分叉、轮内分叉和连续两次分叉。
- 验证近期窗口边界仍可精确回退；新增窗口外自动退到更早摘要、重启后重扫的验收。
- 验证初始边界也被替换时自动重放原范围，修改当前配置不会缩小该范围；替换边界、回退进度和清理旧记录任一步失败都回滚。
- 验证旧任务无法在回退重扫后用相同高度的旧 Hash 覆盖新进度；陈旧回退也不能删除后来提交的摘要。
- 连接真实 Nile 节点，验证创世块、连续区块、交易与回执对应，以及注入 1/4/8 块旧分支 Hash 后的查找、数据库回退和真实区块重扫。

**公共测试网未观察到自然分叉。** 分叉测试使用受控节点分支，或向独立 H2 数据库注入旧分支 Hash；后者查询和重扫使用真实 Nile 区块。Kafka ACK 使用受控 Future，数据库使用 H2 MySQL 模式，部署环境的 MySQL/InnoDB 和 Kafka 联调另行执行。

测试发现并修复：真实 Nile 创世块省略值为 0 的 `number` 和 `timestamp`，现在仅查询创世块时兼容省略字段；其他高度缺字段、显式 null 仍拒绝读取。真实响应保存为 `src/test/resources/samples/tron/nile-genesis-block.json`。

## 六、看代码的顺序

1. `HeadBlockScanJob`：触发扫块，成功回退后正常结束。
2. `HeadBlockScanService`：检查、读取、解析、发送、推进。
3. `HeadBlockContinuityService`：检查末块和下一块，触发分叉回退。
4. `HeadBlockAncestorFinder`：固定节点，二分查找并复查共同区块。
5. `algorithm.BinarySearch`：查找最后匹配高度的独立算法。
6. `HeadScanProgressService`：初始化、提交、清理、回退的手动事务。

整条流程样本测试：`HeadBlockScanAcceptanceTest`。
真实测试网验收：`TronNodeTestnetAcceptanceTest`。

# 阶段 6：充值发现闭环设计

阶段 6 负责把 Scanner 识别出的充值事实可靠发送到 Kafka。`wallet-chain-server` 消费消息，完成币种、地址和幂等校验并创建确认中的充值记录。Scanner 收到 Kafka Broker ACK 后才能推进 `HEAD_BLOCK` 检查点。

## 1. 充值发现事件契约

共享事件定义在 `wallet-chain-server/chain-client`：

```text
Topic: wallet.chain.deposit.discovered
Key:   chainCode + ":" + chainNetwork
Value: ObservedBlockEvent
```

Scanner 按区块发送，一个 Kafka 消息包含本区块识别出的全部充值事实。同一链网络始终使用相同 Key，使消息进入同一分区并保持发送顺序。

## 2. 区块事件

`ObservedBlockEvent` 保存区块公共信息：

| 字段 | 说明 |
|---|---|
| `chainCode` | 链编码，例如 TRON |
| `chainNetwork` | 当前网络，例如 MAINNET、NILE |
| `blockNumber` | 当前区块高度 |
| `blockHash` | 当前区块 ID 或 Hash |
| `parentBlockHash` | 父区块 ID 或 Hash |
| `blockTimestamp` | 链上区块时间 |
| `deposits` | 本区块识别出的充值事实列表 |

父区块 Hash 用于后续区块连续性和未固化分叉校验。

## 3. 充值事实

`DepositDiscoveryEvent` 保存单条充值事实：

| 字段 | 说明 |
|---|---|
| `currency` | 币种编码，例如 TRX、USDT |
| `contractAddress` | TRC20 合约地址；原生币为空字符串 |
| `txId` | 链上交易 ID |
| `eventIndex` | 交易内稳定事件序号 |
| `fromAddress` | 外部付款地址 |
| `toAddress` | 平台充值地址 |
| `rawAmount` | 链上最小单位整数金额，使用 `BigInteger` |

区块高度、Hash 和时间位于外层事件，不在每条充值事实中重复保存。

## 4. 发送与检查点顺序

```text
Scanner 解析一个区块
→ 构建 ObservedBlockEvent
→ 发送 Kafka 并等待 Broker ACK
→ ACK 成功后，在同一个数据库短事务中保存区块摘要并推进 HEAD_BLOCK
```

没有充值事实的区块不发送消息，也要在短事务中保存摘要并推进检查点。

必须先等待 Kafka ACK，再更新数据库检查点，禁止反向执行。

| 失败位置 | 处理结果 |
|---|---|
| Kafka 发送失败 | 不推进检查点，下轮重新扫描同一高度 |
| Kafka 已成功，检查点更新失败 | 重复扫描并再次发送，由链服务幂等去重 |
| 链服务消费失败 | 不提交失败消息的位点，间隔 5 秒重试同一条消息 |

该顺序允许重复投递，避免因投递失败提前推进进度。结合本章第 9 节的分叉恢复机制、节点历史数据可读取和消费端幂等，Scanner 可以从检查点重放，因此不另建 Outbox 表。

## 5. 幂等规则

单条充值事实使用以下稳定唯一键：

```text
chainCode + chainNetwork + txId + eventIndex
```

Kafka 消息重复投递、Scanner 重启补扫和消费重试最终都会收敛到同一条 `chain_deposit`。

## 6. 链服务幂等接收

链服务由独立 Kafka 消费入口接收 `ObservedBlockEvent`，业务处理放在 Biz 层：

```text
DepositDiscoveryConsumer
→ 校验当前链与网络
→ 逐条处理 deposits
→ 按 txId + eventIndex 查询已有记录
→ 校验币种配置和平台充值地址
→ 创建 CONFIRMING 状态的 chain_deposit
```

`chain_deposit` 的唯一键：

```text
(chain_code, chain_network, tx_id, event_index)
```

业务查询用于快速跳过重复消息，数据库唯一键用于处理并发重复消费。一个区块内某条充值处理失败时直接抛出异常，由 Kafka 重投当前消息；此前已经成功保存的充值会在重投时被跳过，因此不需要把整个区块放进一个长事务。

充值地址只校验是否为链服务管理的 `DEPOSIT` 地址。地址当前是否已分配或已停用，不影响已经发生的链上入账事实。

### 6.1 消费失败重试

`chain-biz/config/DepositKafkaConfiguration` 为充值消费者提供专用监听容器工厂。监听器关闭自动提交，采用 `RECORD` 模式；业务正常返回后才提交当前消息位点。

```text
第一次消费：数据库连接失败 → 等待 5 秒
第二次消费：数据库仍然不可用 → 再等待 5 秒
第三次消费：充值保存成功 → 提交位点，继续处理下一条消息
```

普通业务异常和消息转换异常都持续重试，避免框架默认重试耗尽后跳过消息。重试由 chain-server 消费端执行；同一消息中已经保存的充值由现有唯一键和幂等逻辑处理。

长期失败会阻塞同分区后续消息，需要通过消费错误日志和积压监控定位并修复。应用重启后能否继续处理，也依赖有效消费位点和 Kafka 消息保留时间。

### 6.2 首次启动与消费位点

充值监听器使用 `auto.offset.reset=earliest`：Kafka 找不到该消费组的有效位点时，从 Topic 各分区最早仍保留的消息开始消费。

例如分区保留了位点 `100～200` 的消息：

- 没有有效消费位点：从 `100` 开始，避免首次启动时略过已有充值消息。
- 已提交下次读取位点 `141`：从 `141` 继续，不会重新从 `100` 开始。

该配置绑定在 `DepositDiscoveryConsumer`，使用者无需额外配置。已经过期删除的消息无法通过 `earliest` 找回，需要补扫恢复。

## 7. Scanner 区块处理编排

`HeadBlockScanJob` 只负责触发，`HeadBlockScanService` 编排完整扫块流程：

```text
确认地址和币种内存索引已经就绪
→ 读取或初始化 HEAD_BLOCK 检查点
→ 检查已扫描末块是否被替换
→ 查询 FullNode 当前 Head 高度
→ 从检查点下一高度顺序读取区块
→ HeadBlockContinuityService 比较父区块 Hash 与检查点是否一致
→ TronBlockParser 解析充值事实
→ 有充值时发送 Kafka 并等待 Broker ACK
→ 在短事务中保存摘要、更新扫描检查点；整百高度同时清理旧摘要
→ 未达到 Head 和单轮上限时继续下一块
```

`DepositDiscoveryPublisher.publishAndWait` 负责构建 Kafka 事件并等待 Broker ACK。扫块服务只有在该方法正常返回后才推进检查点；超时、发送失败或任务线程中断都会抛出带区块高度的异常。

首次没有检查点时，`startBlockHeight` 表示第一块需要扫描的高度。Scanner 通过 FullNode 查询前一区块 ID，原子保存初始检查点和摘要；当 `startBlockHeight=0` 时使用 `-1` 和空 Hash 作为创世块之前的初始位置。

初始化在同一个手动事务中直接插入检查点和初始摘要，成功后返回初始检查点。如果误触发两个初始化任务，唯一键冲突会结束后执行的任务，下一轮读取已经提交的进度继续扫描。

每轮默认最多处理 100 个新区块，可通过 `max-blocks-per-run` 覆盖。空区块不发送 Kafka，仍需保存摘要并推进检查点。有充值的区块必须等待 Broker ACK，发送异常时不会执行检查点更新。

Scanner 只部署一个实例，`HeadBlockScanJob` 只配置一个调度任务，采用单机串行。进度由这个任务顺序写入，不使用显式行锁或并发抢占；进度与摘要仍在一个手动事务中提交。

## 8. 失败重试

扫块任务采用“本轮立即结束、下一轮从检查点恢复”的重试方式，不在业务代码中增加循环重试：

| 失败位置 | 本轮处理 | 下一轮恢复 |
|---|---|---|
| 节点读取失败 | `TronNodeManager` 切换一个备用节点重试；仍失败则结束任务 | 从原检查点的下一高度重新读取 |
| 区块解析失败 | 结束任务，不返回部分解析结果 | 重新读取并完整解析同一高度 |
| Kafka 发送失败或等待 Broker ACK 超时 | 结束任务，不推进检查点 | 重新发送同一区块事件，链服务幂等去重 |
| Kafka 已成功、检查点更新抛出异常 | 结束任务，以数据库实际结果为准 | 重读检查点；未推进则重新发送，已推进则继续下一块 |

XXL-JOB 固定选择一个执行器，阻塞处理策略设为“单机串行”，失败重试次数设为 0，由下一次定时调度继续处理。异常原样抛出，由调度中心记录任务失败；配置失败告警后可通知运营。每轮重新读取数据库检查点，服务重启也遵循相同恢复流程。

等待 Kafka Broker ACK 默认最多 30 秒，可通过 `nb.tron.scanner.kafka-ack-timeout` 覆盖。超时后 Broker 是否已经接收消息可能未知，因此保留原检查点；下次调度重发，链服务按链上事件唯一键幂等处理。

例如检查点为 99：100 处理成功后保存进度 100，101 发送失败则结束本轮，102 不会执行。下一轮读取到进度 100，只重新处理 101。

该策略允许重复读取和重复发送，不允许跳过失败区块。确定性的坏区块数据会持续阻塞当前高度，需要通过任务失败告警介入处理，禁止自动跳过。

## 9. 区块连续性与分叉回退

### 9.1 保存什么

| 表 | 数据 | 作用 |
|---|---|---|
| `tron_scan_checkpoint` | 最后完整处理的高度和 Hash | 记录扫描到哪里 |
| `tron_scanned_block` | 连续保留的最近 2 万条高度和 Hash | 分叉时找到最后相同的区块 |

首次从 1000 开始，保存 999 的高度和 Hash，本轮从 1000 扫描。起点为 0 时保存 -1/空 Hash，不发送负数高度的节点请求。
初始记录按普通摘要清理，不额外长期保留。最早摘要只是查找起点，不代表固化或安全点。

Scanner 负责发现充值和扫描恢复；chain-server 独立核验充值固化结果，确认后才能通知入账。

### 9.2 扫描入口

```text
加载扫描进度 H
→ checkCheckpoint：比较本地与节点同高度 Hash
  ├─ fork=true：handleFork → 查找共同区块 → 事务回退 → 结束本轮
  └─ fork=false：scanNewBlocks → 读取 H+1 → 检查父 Hash
                    → 解析充值 → Kafka ACK → 事务保存摘要和进度
```

每轮检查末块，发现上轮结束后发生的分叉；每块检查父 Hash，发现本轮扫描中发生的分叉。
正常扫描先确定本轮范围。例如已扫 1000、节点到 1200、单次上限 100，本轮依次处理 1001～1100。
下一块接不上时调用 `handleParentHashMismatch()`，内部复用 `handleFork()` 复查。如果末块仍相同，保持进度，冷却本次异常数据节点，下轮重读；扫块入口在处理后结束本轮。

节点高度不足、超时、限流、空响应均作为读取失败；不能当作 Hash 不同，更不能因此回退。

### 9.3 分叉怎么恢复

例如本地扫到 1010，节点替换了 1008～1010：

1. 固定一个 FullNode，先确认末块 1010 已变化、最早保留的摘要仍相同。
2. 二分查找最后相同的 1007；返回前复查末块、1007 和 1008，防止查找期间分支再次变化。
3. 一个手动事务：检查点更新为 1007/H1007，删除 1008～1010 的旧摘要，保留 1007。
4. 本轮结束，下轮从 1008 重扫新分支。

节点读取失败或查找期间分支变化：结束本轮，原进度不变，下轮重新查找。
查找时末块又相同，例如换节点后仍是 1010/H1010：不回退，本轮结束。

**找不到共同区块：** 抛出 `HEAD_SCAN_COMMON_ANCESTOR_NOT_FOUND`，检查点和摘要保持不变，交给 XXL-JOB 按失败告警策略处理。
例如扫到 100000、保留 80001～100000，而共同区块是 79990：无法根据已保留数据确定回退位置，不能跳到最新高度，也不自动从配置起点重扫。

### 9.4 事务与摘要清理

- 正常推进：保存当前区块摘要、更新检查点；Kafka ACK 在事务之前完成。
- 分叉回退：更新检查点、删除共同区块之后的摘要，两步 SQL 一起提交。
- 数据库失败：整个事务回滚，内存检查点也保持原值。
- 消息已发送但提交失败：下轮可以重发，由 chain-server 幂等接收。

默认最近 20000 条连续摘要，每 100 个高度清理一次：

| 已扫高度 | 保留范围 |
|---:|---|
| 30000 | 10001～30000 |
| 30099 | 10001～30099，暂时多保留 99 条 |
| 30100 | 10101～30100 |

普通区块只插入摘要、更新进度。整百高度在同一个事务中按网络和高度范围删除旧摘要，不查询初始边界或计算稀疏锚点。

### 9.5 代码职责

前提：一个 Scanner 实例、一个 `HeadBlockScanJob` 任务，XXL-JOB 配置单机串行。

| 类 | 做什么 |
|---|---|
| `HeadBlockScanService` | 检查分叉，分流到恢复或正常扫块 |
| `HeadBlockContinuityService` | 比较末块和父 Hash，组织分叉处理 |
| `HeadBlockAncestorFinder` | 固定节点，二分查找并复核共同区块 |
| `HeadScanProgressService` | 初始化、提交进度、事务回退、批量清理摘要 |
| 数据库 Service | 只负责查询、插入、更新、删除 |

从 `scanBlocks()` 开始看，再看 `handleFork()` 或 `scanNewBlocks()`。网络请求和 Kafka 发送都在数据库事务之外。

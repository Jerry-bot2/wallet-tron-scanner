# 阶段 6：充值发现闭环设计

阶段 6 负责把 Scanner 识别出的充值事实可靠发送到 Kafka。`wallet-chain-server` 消费消息，完成币种、地址和幂等校验并创建确认中的充值记录。Scanner 收到 Kafka Broker ACK 后才能推进 `HEAD_BLOCK` 检查点。

## 1. 充值发现事件契约

共享事件定义在 `wallet-chain-server/chain-client`：

```text
Topic: wallet.chain.deposit.discovered
Key:   chainCode + ":" + chainNetwork
Value: ObservedBlockEvent
```

Scanner 按区块发送，一个 Kafka 消息包含本区块识别出的全部充值事实。同一链网络始终使用相同 Key，使消息进入同一分区并保持发送顺序。

## 2. 区块事件

`ObservedBlockEvent` 保存区块公共信息：

| 字段 | 说明 |
|---|---|
| `chainCode` | 链编码，例如 TRON |
| `chainNetwork` | 当前网络，例如 MAINNET、NILE |
| `blockNumber` | 当前区块高度 |
| `blockHash` | 当前区块 ID 或 Hash |
| `parentBlockHash` | 父区块 ID 或 Hash |
| `blockTimestamp` | 链上区块时间 |
| `deposits` | 本区块识别出的充值事实列表 |

父区块 Hash 用于后续区块连续性和未固化分叉校验。

## 3. 充值事实

`DepositDiscoveryEvent` 保存单条充值事实：

| 字段 | 说明 |
|---|---|
| `currency` | 币种编码，例如 TRX、USDT |
| `contractAddress` | TRC20 合约地址；原生币为空字符串 |
| `txId` | 链上交易 ID |
| `eventIndex` | 交易内稳定事件序号 |
| `fromAddress` | 外部付款地址 |
| `toAddress` | 平台充值地址 |
| `rawAmount` | 链上最小单位整数金额，使用 `BigInteger` |

区块高度、Hash 和时间位于外层事件，不在每条充值事实中重复保存。

## 4. 发送与检查点顺序

```text
Scanner 解析一个区块
→ 构建 ObservedBlockEvent
→ 发送 Kafka 并等待 Broker ACK
→ ACK 成功后，在同一个数据库短事务中保存区块摘要并推进 HEAD_BLOCK
```

没有充值事实的区块不发送消息，也要在短事务中保存摘要并推进检查点。

必须先等待 Kafka ACK，再更新数据库检查点，禁止反向执行。

| 失败位置 | 处理结果 |
|---|---|
| Kafka 发送失败 | 不推进检查点，下轮重新扫描同一高度 |
| Kafka 已成功，检查点更新失败 | 重复扫描并再次发送，由链服务幂等去重 |
| 链服务消费失败 | 不提交消费位点，由 Kafka 消费重试 |

该顺序允许重复投递，避免因投递失败提前推进进度。结合本章第 9 节的分叉恢复机制、节点历史数据可读取和消费端幂等，Scanner 可以从检查点重放，因此不另建 Outbox 表。

## 5. 幂等规则

单条充值事实使用以下稳定唯一键：

```text
chainCode + chainNetwork + txId + eventIndex
```

Kafka 消息重复投递、Scanner 重启补扫和消费重试最终都会收敛到同一条 `chain_deposit`。

## 6. 链服务幂等接收

链服务由独立 Kafka 消费入口接收 `ObservedBlockEvent`，业务处理放在 Biz 层：

```text
DepositDiscoveryConsumer
→ 校验当前链与网络
→ 逐条处理 deposits
→ 按 txId + eventIndex 查询已有记录
→ 校验币种配置和平台充值地址
→ 创建 CONFIRMING 状态的 chain_deposit
```

`chain_deposit` 的唯一键：

```text
(chain_code, chain_network, tx_id, event_index)
```

业务查询用于快速跳过重复消息，数据库唯一键用于处理并发重复消费。一个区块内某条充值处理失败时直接抛出异常，由 Kafka 重投当前消息；此前已经成功保存的充值会在重投时被跳过，因此不需要把整个区块放进一个长事务。

充值地址只校验是否为链服务管理的 `DEPOSIT` 地址。地址当前是否已分配或已停用，不影响已经发生的链上入账事实。

## 7. Scanner 区块处理编排

`HeadBlockScanJob` 只负责触发，`HeadBlockScanService` 编排完整扫块流程：

```text
确认地址和币种内存索引已经就绪
→ 读取或初始化 HEAD_BLOCK 检查点
→ 检查已扫描末块是否被替换
→ 查询 FullNode 当前 Head 高度
→ 从检查点下一高度顺序读取区块
→ HeadBlockContinuityService 校验父区块 Hash 与检查点是否一致
→ TronBlockParser 解析充值事实
→ 有充值时发送 Kafka 并等待 Broker ACK
→ 在短事务中保存摘要、条件更新 HEAD_BLOCK 检查点并清理窗口外摘要
→ 未达到 Head 和单轮上限时继续下一块
```

`DepositDiscoveryPublisher.publishAndWait` 负责构建 Kafka 事件并等待 Broker ACK。扫块服务只有在该方法正常返回后才推进检查点；超时、发送失败或任务线程中断都会抛出带区块高度的异常。

首次没有检查点时，`startBlockHeight` 表示第一块需要扫描的高度。Scanner 通过 FullNode 查询前一区块 ID，原子保存初始检查点和摘要；当 `startBlockHeight=0` 时使用 `-1` 和空 Hash 作为创世块之前的初始位置。

初始化在同一个手动事务中直接插入检查点和初始摘要，成功后返回初始检查点。如果误触发两个初始化任务，唯一键冲突会结束后执行的任务，下一轮读取已经提交的进度继续扫描。

每轮默认最多处理 100 个新区块，可通过 `max-blocks-per-run` 覆盖。空区块不发送 Kafka，仍需保存摘要并推进检查点。有充值的区块必须等待 Broker ACK，发送异常时不会执行检查点更新。

检查点使用原高度和原 Hash 作为更新条件。即使误触发两个扫块任务，也只有一个任务能够更新；另一个任务会结束，已经重复发送的充值由链服务唯一键去重。Hash 条件同时防止分叉回退后，旧任务在相同高度覆盖新分支的进度。

## 8. 失败重试

扫块任务采用“本轮立即结束、下一轮从检查点恢复”的重试方式，不在业务代码中增加循环重试：

| 失败位置 | 本轮处理 | 下一轮恢复 |
|---|---|---|
| 节点读取失败 | `TronNodeManager` 切换一个备用节点重试；仍失败则结束任务 | 从原检查点的下一高度重新读取 |
| 区块解析失败 | 结束任务，不返回部分解析结果 | 重新读取并完整解析同一高度 |
| Kafka 发送失败或等待 Broker ACK 超时 | 结束任务，不推进检查点 | 重新发送同一区块事件，链服务幂等去重 |
| Kafka 已成功、检查点更新抛出异常 | 结束任务，以数据库实际结果为准 | 重读检查点；未推进则重新发送，已推进则继续下一块 |
| 检查点被其他任务推进 | 当前任务失败退出 | 下一轮重新读取数据库最新检查点 |

XXL-JOB 固定选择一个执行器，阻塞处理策略设为“单机串行”，失败重试次数设为 0，由下一次定时调度继续处理。异常原样抛出，由调度中心记录任务失败；配置失败告警后可通知运营。每轮重新读取数据库检查点，服务重启也遵循相同恢复流程。

等待 Kafka Broker ACK 默认最多 30 秒，可通过 `nb.tron.scanner.kafka-ack-timeout` 覆盖。超时后 Broker 是否已经接收消息可能未知，因此保留原检查点；下次调度重发，链服务按链上事件唯一键幂等处理。

例如检查点为 99：100 处理成功后保存进度 100，101 发送失败则结束本轮，102 不会执行。下一轮读取到进度 100，只重新处理 101。

该策略允许重复读取和重复发送，不允许跳过失败区块。确定性的坏区块数据会持续阻塞当前高度，需要通过任务失败告警介入处理，禁止自动跳过。

## 9. 区块连续性与分叉回退

### 9.1 保存的数据与职责

- `tron_scan_checkpoint`：最后完整处理成功的区块高度和 Hash。
- `tron_scanned_block`：最近一段已扫描区块的高度和 Hash，主键 `(chain_network, block_number)`。
- 最早的一条仅代表历史查找的下界，**不代表固化或安全点**。
- Scanner 只读 FullNode，处理 Head 连续性；chain-server 独立完成充值固化确认。

首次从 B 开始扫描时，保存 FullNode 的 B-1 区块头作为初始进度和摘要，不必等待固化。B=0 时保存 -1/空 Hash，不请求负数区块。

### 9.2 正常扫描

```text
读取数据库检查点 H
→ 核对 FullNode 的 H Hash：一致则继续，不一致则查找共同区块
→ 查询最新 Head 高度
→ 读取 H+1 的区块与回执，再次核对该高度的 Hash 未变
→ 连续性检查：高度必须加一，父 Hash 必须等于本地 H Hash
→ 解析充值，发送 Kafka 并等待 ACK
→ 短事务：保存摘要 + 条件推进检查点 + 清理窗口外摘要
→ 继续下一块
```

即使没有新区块，也检查末块，避免漏掉同高度替换。新区块父 Hash 不一致，但重新查询的末块仍匹配时，冷却返回异常区块的节点，本轮结束；下轮重新选择节点读取，不做同高度回退。找到共同区块后的正常回退不冷却节点。

例如第一次读到 `1011/A`，回执读完后再次读取却是 `1011/B`：丢弃本次数据，由节点管理器整体切换备用节点重读；没有可用备用节点时结束本轮，进度保持不变。复核期间节点请求失败，也不能使用之前读到的区块和回执。

### 9.3 二分查找最近的共同区块

1. 固定一个已经同步到 H 的 FullNode，本次查找全部请求使用该节点。
2. 确认最早保留的摘要仍与节点匹配；不匹配说明历史不够，停止并报错。
3. 左边是相同区块，右边是不同区块。比较中间高度：相同向右找，不同向左找。
4. 两边只差一块时，左边就是最近的共同区块。
5. 返回前复查末块未改变、共同区块仍相同、下一条保留摘要仍不同。近期连续区间的下一条就是下一块；旧历史允许存在间隔。查找期间链变化或请求失败，本轮结束，下轮重新查找。

例如本地保存 1000～1010，节点上的 1000～1007 相同，1008～1010 已被替换：

| 步骤 | 左边相同 | 右边不同 | 比较中点 | 结果 |
|---|---:|---:|---:|---|
| 1 | 1000 | 1010 | 1005 | 相同，左边改为 1005 |
| 2 | 1005 | 1010 | 1007 | 相同，左边改为 1007 |
| 3 | 1007 | 1010 | 1008 | 不同，右边改为 1008 |
| 结束 | 1007 | 1008 | — | 返回 1007 |

区块 Hash 包含祖先关系，同一个稳定分支与本地分支的共同部分是连续前缀，因此可以二分。1000 条历史最多约 10 次中点比较，另加首尾和边界核验。固定节点与复查用于发现查找期间的变化，不能代替充值最终固化确认。

### 9.4 回退、清理与失败处理

找到共同区块 1007 后，在一个手动事务内：

```text
锁定检查点，核对原高度和 Hash
→ 核对数据库里的 1007 摘要
→ 检查点改为 1007，删除 1008 之后的旧摘要
→ 提交事务，结束本轮
→ 下轮从 1008 重扫新分支
```

`blockHistorySize` 默认 **10000 条**，通常不用配置。采用两种保留方式，仍使用同一张摘要表：

1. 最近 1 万条连续保存，普通分叉可以精确找到最后相同的区块。
2. 更早历史每 1000 块留一条，最初起点始终保留；超出近期窗口时仍能查找更早的共同区块。

例如从 100 开始扫描，已到 20000：连续保留 10001～20000，旧历史保留 99、1000、2000、……、10000。真正共同区块为 8500 时，8000 相同、9000 不同，自动退到 8000；下一轮从 8001 重扫，只比精确回退多重扫 500 块。

二分比较高度 8500 时，数据库查询“不超过 8500 的最近摘要”，得到 8000。返回前核验下一条保留摘要 9000 仍不同。算法不要求旧摘要连续，仍固定同一 FullNode，查找期间分支变化则整轮重试。

清理、摘要插入、进度更新在同一事务中；任何一步失败全部回滚。旧历史只保留高度和 Hash，正常每扫描 1000 块增加一条长期摘要，不保存交易数据，也不加载到内存。

| 情况 | 处理 |
|---|---|
| 节点落后、超时、空响应 | 结束本轮，保留原进度；不当作 Hash 不同 |
| 二分中途节点失败 | 当前节点进入冷却期；下轮重新选择节点，从头查找，不中途混用主备结果 |
| 新块父 Hash 不一致，但末块仍匹配 | 冷却返回该新块的节点，结束本轮；下轮换节点读取，不修改进度 |
| 查找期间链变化 | 结束本轮，不修改数据库，下轮重新查找 |
| 最近 1 万条都不匹配 | 自动继续查找更早的稀疏摘要，事务回退后下轮重扫，不因近期窗口被清理而卡住 |
| 最初扫描边界也不匹配 | 自动读取边界的新 Hash，事务替换边界、回退检查点并删除后续旧摘要；下轮从该边界的下一块重放整个已记录范围 |
| 本地摘要缺失 | 报 `HEAD_SCAN_HISTORY_INVALID`，停止本轮，不用节点当前 Hash 伪造旧历史 |
| 回退事务失败或并发进度变化 | 整体回滚，下轮重读数据库 |
| 分叉回退事务成功 | Job 记录警告，正常结束本轮；下一轮重扫，不触发 XXL-JOB 失败策略 |

1 万是近期连续窗口，已记录的更早范围没有整体删除。稀疏保留使窗口外分叉也能自动恢复，找到共同摘要时最多额外重扫 999 块。

如果连原始 99 也被替换，已经找不到共同摘要：新的 99 Hash 作为完整重放的边界，在一个事务中替换边界记录、将检查点退到 99、删除 100 之后的旧摘要。下轮从 100 重放，不将新边界当作旧分支的共同区块。当前配置即使改为从 150 扫描，也不会缩小这段已有范围。这是极端情况下的自动兜底，普通分叉不会从头重扫。

数据库损坏或历史已被外部删除仍不能保证自动修复。普通节点读取可以即时切换一次备用节点；共同区块查找保持同一分支视图，失败后下一轮整体重试。节点读取失败不会触发完整重放。

### 9.5 类的职责

| 类 | 职责 |
|---|---|
| `HeadBlockScanService` | 编排检查、读取、解析、发送和推进进度 |
| `HeadBlockContinuityService` | 检查末块和父 Hash，发现分叉后触发回退 |
| `HeadBlockAncestorFinder` | 固定 FullNode，提供 Hash 比较，调用算法并复核结果 |
| `algorithm.BinarySearch` | 二分查找最后满足条件的高度，比较方式由调用方提供 |
| `HeadScanProgressService` | 初始化、推进、清理与回退的手动事务 |
| `ITronScannedBlockService` | 摘要查询、插入及按高度删除 |
| `TronNodeManager` / `TronBlockHeaderReader` | 选择合格节点，提供本次查找固定节点的读取能力 |

### 9.6 首次部署与旧版本迁移

新库直接执行 `sql/wallet-tron-scanner-ddl.sql`。已有库执行 `sql/migrations/20261005-01-add-tron-scanned-block.sql`，该脚本只创建摘要表，不自动重置进度。

已有 Head 检查点但没有对应摘要时，程序报 `HEAD_SCAN_HISTORY_INVALID` 并停止该轮扫描。**不能拿节点当前 Hash 填充旧扫描历史，也不能只把旧检查点补成历史下界。**

旧版本初始化回放步骤：

1. 停止当前网络的扫块任务，备份 checkpoint 和现有摘要。
2. 确认 `start-block-height` 是原来约定的扫描起点，没有调高；该起点之前不属于本 Scanner 的扫描范围。
3. 在同一个数据库事务中删除该网络的 checkpoint 和摘要，不删除监控地址、不删除 chain-server 的充值记录。
4. 恢复任务，程序从原起点前的 FullNode 区块头初始化，逐块重放并生成摘要；已发送的充值由链服务幂等处理。
5. 这是从缺少历史摘要的旧版本升级时的一次性回放，日常分叉恢复在已保留摘要中查找最近的共同区块。

已有摘要的库不需要改表，新保留策略直接生效。过去已经删除的 Hash 不能重新从当前节点还原；新策略从现有最早摘要开始长期保留，不自动删除或重置现有进度。

禁止自动执行上述删除。备份、原始起点和停止任务都需要部署时确认。本次代码调整没有连接或修改任何运行中的数据库。

### 9.7 验收与资金边界

自动测试覆盖：普通续扫、空块、同高度替换、父 Hash 不一致、异常节点冷却后使用备用节点、回执读取期间区块替换、Hash 复核请求失败、二分查找最近共同区块、固定节点读取、查找期间链变化、超出近期窗口后自动恢复、稀疏历史查询及压缩、事务回滚、并发提交、重启后发现替换分支充值、回退成功正常结束任务和真实异常继续报错。

数据库测试使用真实 MyBatis Mapper、H2 MySQL 模式和 Spring 事务；不替代部署环境的 MySQL/InnoDB、真实 TRON 节点和 Kafka 联调。

旧分支的充值事件可能已经被 chain-server 接收。阶段 7 必须依据固化交易及回执处理这些记录：一次查询为空不能判死；同一交易重新打包时核实实际固化区块和转账内容；已确认结果不能被晚到的 Head 消息覆盖；所有入账操作保持幂等。这些属于链服务确认流程，不在本次 Scanner 6.5 中实现。

### 10.3 复跑方式
